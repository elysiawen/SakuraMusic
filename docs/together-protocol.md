# 一起听（房间）协议

面向客户端开发者。本文描述「一起听」——**多人共享同一个播放现场**，任一方都能切歌、
暂停、拖动进度、点歌，所有人听到的是同一首歌的同一进度。

- 服务端实现：`gateway/src/services/rooms.ts`、`gateway/src/routes/rooms.ts`
- 参考客户端（网页）：`web/src/stores/room.ts`、`web/src/components/TogetherPanel.vue`
- 参考客户端（安卓）：`client-android/app/src/main/java/com/sakura/music/core/player/RoomSync.kt`、
  `…/ui/components/TogetherSheet.kt`
- 参考实现里的同步算法：`web/src/utils/sync.ts`（与「多设备跟随」共用）
- 与「多设备管理」的区别见 `connect-protocol.md`；**播放本身**（取流、音质、歌词、音乐库）仍见 `API.md`

## 0. 房间类型：双人房 / 多人房

房间带一个显式的 `kind` 字段，**权限、容量、客户端界面都由它决定**：

| `kind` | 说明 | 容量 | 管理权 | 状态 |
|---|---|---|---|---|
| `duo` | 双人房。**人人平权**——没有房主，任一成员都能播放控制与解散 | 2 | 无成员管理 | **已支持** |
| `group` | 多人房。房主独占管理权（解散 / 踢人），播放控制仍人人可用 | 10 | 房主 | **尚未开放** |

要点：

- `duo` 房里**不存在 `owner`**：创建者在快照里同样是 `role: 'member'`。
  `ownerUserId` 只是「谁建的房」这个记录，不构成权限。
- 服务端只放行 `duo`；创建 `group` 会返回 `400 room_kind_unsupported`。
  `group` 的数据模型、协议字段与客户端界面分支都已就位，启用时服务端放开即可。
- 客户端 UI 应当**分别实现**两套：双人房用「两人对置」的专用布局，
  多人房用成员列表 + 管理区。不要用一套界面硬套两种语义。

---

## 1. 它是什么 / 不是什么

**是**：一个**服务端权威**的共享播放现场。房间持有权威的（队列 + 播放态 + 进度），
成员的任何操作都提交给网关，网关改写后广播给所有成员；每个成员把本地播放器**镜像**到房间状态。

**不是**：

- 不是把音频从一台设备推给另一台。音频永远由**真正出声的那台设备自己**去取，
  本协议**一个音频字节都不传**（只传取流坐标 `sources`）。
- 不是好友系统：用**房间码 / 邀请链接**入房，没有好友关系与申请流程。
- 状态**不落库**：网关重启后房间清空，重连之后要按 7.2 判断自己是「接回席位」还是「旁观」。
- 不是「一个账号的多台设备各放一遍」：一个账号只占**一个席位**（只有一台设备在出声），
  其余设备是旁观，可以把播放**转移**过来（见 7.8）。

---

## 2. 为什么是「服务端权威」

多设备协议（`connect-protocol.md`）是「客户端镜像客户端」，前提是有确定的 leader 设备。
而房间里人人可以操作，若各报各的状态就会互相拉扯；共享队列（点歌）也需要一份权威队列。
所以：

```
成员操作 ──POST /api/rooms/action──▶ 网关（权威：队列 + 播放态 + 进度）
                                        │ 改写状态 + 盖 positionAt
     所有成员 ◀──SSE `room-playback`─────┘
     └─ 本地播放器镜像房间状态
```

服务端在每个动作前先把自己的进度推进到「现在」（`position += now - positionAt`），
再应用变更并重新盖章。**因此客户端不需要上报进度**，也不存在「两端时钟不一致导致进度飘」。

## 3. 连接与事件

房间事件复用**设备已有的那条 SSE 长连接**（`GET /api/connect/events`），
所以房间里**不需要**另开一条连接。事件名：

| 事件 | 时机 | 载荷 |
|---|---|---|
| `room` | 加入 / 退出 / 席位转移 / 解散 / 队列变化（加歌、删歌、换歌单） | `{ room: RoomView \| null, serverNow, reason?, deviceName? }` |
| `room-playback` | 播放 / 暂停 / 切歌 / 拖动进度 / 自然播完 / 跳过 | `RoomPlaybackView & { serverNow }` |

`room: null` 表示**这个房间不再作用于本机**，但两种原因该怎么处理完全不同，看 `reason` 分：

| `reason` | 场景 | 客户端该做什么 | 提示语 |
|---|---|---|---|
| 缺省 | 房间真的没了：被解散（对方结束 / 房主解散），或本机已被移出 | 本地收尾，回到个人播放；按「是不是自己发起的」给提示（见 7.4） | 「对方结束了一起听」/「房主结束了一起听」 |
| `seat_taken` | **席位被同一账号的另一台设备接走**了（见 7.8）；`deviceName` 是接走那台的名字。**房间没散** | **降级为旁观**：房间继续显示，只把播放器还给用户自己的队列 | 「一起听已转移到「X」，本机改为旁观」 |

### 事件发给谁

**发给「成员账号下的所有在线设备」**，而不只是占着席位的那台：同一账号的第二台设备
（手机 + 平板）也要看得到这个房间，只是它那不叫「在本机播放」（见 7.8）。
所以收到快照 ≠ 本机在放——**本机在放与否看 `members[].me`**。

两个事件都带 `serverNow`：客户端用它算「本机时钟 − 服务端时钟」的偏移，供进度推算（见第 6 节）。

### RoomView

```json
{
  "code": "7K2QMF",
  "kind": "duo",
  "capacity": 2,
  "ownerUserId": "12",
  "members": [
    {
      "userId": "12", "nickname": "小樱", "avatar": null,
      "deviceId": "ab.cd", "deviceName": "Windows · Chrome",
      "kind": "web", "online": true, "me": true, "mine": true, "role": "member"
    }
  ],
  "queue": [ /* TrackSnapshot[] */ ],
  "index": 0,
  "version": 3,
  "togetherSeconds": 4980,
  "togetherSessionSeconds": 300,
  "togetherCounting": true
}
```

- `kind` / `capacity`：房间类型与人数上限，界面据此分岔（见第 0 节）。
- `members` 恒为**全量**。
- `me` 是按**接收设备**逐个填的：同一条广播，每台设备拿到的 `me` 不同。
  它只对「席位就在这台设备上」的那台为 `true`——同一账号的另一台收到的全是 `false`。
  **它是「本机要不要镜像播放」的唯一判据**，别拿 `members.length` 或账号 id 去推。
- `mine` 也是按接收方逐个填的：标记**这条成员属于收件人的账号**（席位可能挂在它的另一台
  设备上）。客户端靠它认出「哪条是我这边的」，不必自己拿登录态里的 userId 比对——
  那点登录态在客户端不一定随时都在。恒有 `me → mine`。
- `online` 反映**这台设备当前是否连着 SSE**；成员席位与连接是两回事（见 7.3）。
- `members[].kind` 是**设备形态**（web/android/windows），与房间类型 `kind` 同名但不是一回事。
- `members[].role`：`duo` 房恒为 `member`；`group` 房里创建者是 `owner`。
- `version` 是队列版本号，队列一变就递增；客户端可用它做去重。
- `togetherSeconds` / `togetherSessionSeconds` / `togetherCounting`：一起听时长，见 7.5。

### RoomPlaybackView

```json
{
  "index": 0,
  "playing": true,
  "position": 42.4,
  "positionAt": 1758600000000,
  "duration": 269,
  "track": {
    "key": "netease:186016",
    "title": "晴天",
    "artists": "周杰伦",
    "album": "叶惠美",
    "cover": "https://…",
    "durationMs": 269000,
    "sources": [{ "platform": "netease", "id": "186016" }]
  },
  "mode": "all",
  "serverNow": 1758600000000,
  "skipReason": "unplayable",
  "skippedTitle": "夜曲"
}
```

- `track` 为 `null` 表示房间当前没有可播放的曲目（空房间或已播完）。
- `position` / `duration` 单位是**秒**，`track.durationMs` 是**毫秒**（与多设备协议同一约定）。
- `mode` 是房间的播放模式（`order` / `all` / `one` / `shuffle`，见 5.3）。客户端把它当作
  **本机模式选择器的唯一真相**：收到就对齐本机；用户点选时改走 `setMode`，不要只改本机。
- `skipReason` / `skippedTitle` 只在「有一方播不了、全员跳过」这一帧出现（见 6.3）。

### TrackSnapshot

服务端**不解析曲目实体**，只保存展示与取流所需的最小字段：

```ts
{
  key: string,            // 曲目唯一键，如 "netease:186016"（去重/定位都靠它）
  title: string,
  artists: string,        // 已拼好的字符串 "周杰伦 / 费玉清"，不是数组
  album: string,
  cover: string | null,
  durationMs: number,
  sources: [{ platform, id, mid?, numericId? }]   // 取流坐标，必须有
}
```

客户端的曲目模型（如 Web 的 `UnifiedTrack`）需要一层映射：镜像时至少保留
`key / title / artists / album / cover / durationMs / sources`。缺 `sources` 就播不出来。

## 4. 接口总览

全部在网关 `/api` 前缀下，鉴权与会话同一套（HttpOnly Cookie `sakura_session`）。未登录一律 `401`。

| 方法 | 路径 | 作用 |
|---|---|---|
| POST | `/api/rooms/create` | 创建房间，创建者入座。可带初始队列 |
| POST | `/api/rooms/join` | 凭房间码加入 |
| POST | `/api/rooms/leave` | 退出（房间还有人就保留） |
| POST | `/api/rooms/dissolve` | 解散房间（v1 任一成员都可以） |
| POST | `/api/rooms/action` | 提交播放操作 |
| GET | `/api/rooms/overview` | 我的**一起听总览**（账户中心用），见 7.6 |
| GET | `/api/rooms/overview/:partnerId` | 与某位好友的**每次明细**，见 7.7 |
| GET | `/api/rooms/:code` | 入房前预览（是否存在、都有谁、在放什么） |

所有请求都要带 `deviceId`——它用于定位 SSE 连接与房间席位。

### 4.1 create

```
POST /api/rooms/create
{ "deviceId": "ab.cd", "name": "客厅", "deviceKind": "web",
  "kind": "duo", "queue": [ /* UnifiedTrack[]，可选 */ ], "index": 0,
  "mode": "all" }
→ { "code": "7K2QMF" }
```

- `deviceKind` 是**设备形态**（web / android / windows），缺省按 `web` 处理。
- `kind` 是**房间类型**，缺省 `duo`；目前只有 `duo` 会被放行（见第 0 节）。
- 不带 `queue` 时创建空房间（随后用 `setQueue` 填）。
- `mode` 是**初始播放模式**（`order` / `all` / `one` / `shuffle`），缺省 `order`。
  客户端一般把自己当前的模式传上来，免得刚建好就被默认值改掉；加入方一律以房间的
  `mode` 为准（见 5.3）。

### 4.2 join

```
POST /api/rooms/join
{ "code": "7K2QMF", "deviceId": "ab.cd", "name": "手机", "deviceKind": "android" }
→ { "ok": true }
```

房间码不区分大小写。加入后服务端会通过 SSE 推 `room` 与 `room-playback`。
无需指定 `kind`——房间类型由房间自己决定，客户端从 `room.kind` 读取。

**`join` 的语义是「把席位接过来」**：同一账号在房间里只有一个席位（7.1），
所以第二台设备 `join` 等于把播放从原来那台搬过来（7.8 的「转移到本机」走的就是它）。
被顶掉的那台会收到 `room: null` + `reason: 'seat_taken'`，紧接着还会收到一份全量快照；
它据此**降级为旁观**——房间继续显示，只是不在它那台上放（见 7.8）。

### 4.3 leave / dissolve

```
POST /api/rooms/leave      { "deviceId": "ab.cd" } → { "ok": true }
POST /api/rooms/dissolve   { "deviceId": "ab.cd" } → { "ok": true }
```

`leave` 只退自己；房间空了即销毁。`dissolve` 直接解散，所有成员会收到 `room: null`。

**双人房不要用 `leave`**：两个人里走一个，房间只剩一个人，一起听就没有意义了——
双人房的「结束」一律走 `dissolve`（见 7.4）。

### 4.4 action

```
POST /api/rooms/action
{ "deviceId": "ab.cd", "action": "seek", "payload": { "position": 42 } }
→ { "ok": true }
```

`ok` 只代表服务端**已接受并广播**，不代表对方已执行到位（进度靠各自的镜像循环收敛）。

**旁观设备发不出这些动作**：鉴权按「席位设备」查（`deviceRoom`），第二台设备连成员都不是，
一律 `404 room_not_found`。想控制就先「转移到本机」（见 7.8）。

### 4.5 preview（入房前看一眼 / 冷启动对账）

```
GET /api/rooms/:code
→ {
    "code": "7K2QMF", "kind": "duo", "capacity": 2,
    "members": [ { "nickname": "小樱", "avatar": null } ],
    "playing": true, "track": { /* TrackSnapshot | null */ },
    "mine": "ab.cd"
  }
```

`mine` 是**本账号在这个房间的席位挂在哪台设备上**（`null` = 本账号不在房间里）。
只回调用者自己账号的席位，不泄露别人用什么设备。

客户端拿它回答一个必须回答的问题：**重建 / 刷新之后，该不该把席位接回来？**

- `mine === null`（席位空着）或 `mine === 本机 deviceId` → 可以直接 `join`；
- `mine === 我另一台设备的 deviceId` → 一起听跟着那台走了，本机**只能旁观**，
  此时再 `join` 就是把播放从对面抢过来（见 7.8）。

## 5. action 全表

| action | payload | 语义 |
|---|---|---|
| `play` | — | 开始/继续。若已播到结尾则从头开始 |
| `pause` | — | 暂停 |
| `next` / `prev` | — | 切歌（到队尾循环）。`prev` 在播过 4 秒后是「回到本曲开头」 |
| `playAt` | `{ index }` | 播放队列第 N 首 |
| `seek` | `{ position }` | 跳到第 N 秒 |
| `add` | `{ track }` | 加歌到队尾（按 `key` 去重）。不打断当前播放 |
| `playNow` | `{ track }` | 点歌并播放：不在队列里就追加，然后跳到它从头播 |
| `remove` | `{ index }` | 从队列移除 |
| `setQueue` | `{ queue, index? }` | 换歌单：整体替换队列并清空跳过记录，从第一首开始播 |
| `setMode` | `{ mode }` | 改播放模式（`order` / `all` / `one` / `shuffle`，**两端共享**，见 5.3） |
| `ended` | `{ trackKey }` | 自然播完上报（见 5.1） |
| `unplayable` | `{ trackKey }` | 本机播不了这首，请全员跳过（见 5.2） |

不在表里的 action 一律 `400 unknown_action`；非房间成员一律 `403 not_a_member`（未入房是 `404 room_not_found`）。

队列上限 **200 首**、总大小 ≤ **512 KB**（`400 queue_too_large` / `queue_full`）。

### 5.1 自然播完：`ended` 是幂等的

房间里两端会**几乎同时**算出曲目结束。上报 `ended` 时带上**刚播完那首的 key**，
服务端只在它等于房间当前曲目时才前进——另一端迟到的上报会被忽略。所以「自然播完」**只会切一次**。

**往哪走由房间的播放模式决定**：

| `mode` | 自然播完之后 |
|---|---|
| `order` 顺序播放 | 往后一首；到队尾停下（`playing: false`）。**这就是加 `mode` 之前的行为** |
| `all` 列表循环 | 往后一首；到队尾回到队首 |
| `one` 单曲循环 | 不换曲目，当前这首从头再放 |
| `shuffle` 随机播放 | 随机换一首（排除当前这首） |

往后找时**跳过本房间已标记「播不了」的曲目**（见 5.2）：否则会自动落到一首放不出来的歌上，
两端各自再报一次 `unplayable`，白绕一圈。队尾/随机都没得挑时，`all` 与 `shuffle` 会回到
当前这首再放一遍，而不是空转。

只有**自动接下一首**看模式；手动 `next` / `prev` 仍旧是线性的（`next` 到队尾循环），
与本地播放器的手感一致。

### 5.2 一方播不了 → 全员跳过

只有**确定性播不了**才上报 `unplayable`：

| 失败类型 | 处理 |
|---|---|
| 无音源 / 版权不可用 / 会员权限不足 / **仅试听片段** | → 上报 `unplayable`，全员跳过 |
| 网络错误 / 超时 / 上游 5xx | → 退避重试，**不要**上报（否则一次卡顿就跳掉整首歌） |

服务端把这首歌的 key 记进房间的「已跳过」集合，然后跳到后面第一首没被跳过的曲目；
若后面都跳过了就停下（`playing: false`）。换歌单（`setQueue`）会清空这个集合。

参考实现在 Web 端是由播放器给出的失败分类信号驱动的（`player.ts` 的 `lastFailure`，
`kind: 'unplayable' | 'transient'`）。Android 端需要一条等价的信号：
把「解析取流地址返回 4xx / 只拿到试听」判为 `unplayable`，网络类错误判为 `transient`。

### 5.3 播放模式是共享的：`setMode`

```
POST /api/rooms/action
{ "deviceId": "ab.cd", "action": "setMode", "payload": { "mode": "all" } }
```

`mode` ∈ `order` / `all` / `one` / `shuffle`（与客户端的模式枚举一一对应）；不合法 → `400 invalid_mode`。

- **它和队列、播放态一样是房间的共享状态**：任一方改，服务端随下一帧 `room-playback`
  把 `mode` 广播给两端，两端的选择器都跟着变。
- **为什么必须上报、不能只改本机**：房间里「自然播完往哪走」由服务端按房间模式决定（5.1）。
  只改本机的话，播完时本机和服务端各按各的走 —— 一端自动接了下一首，另一端停在原地。
- 入房后客户端要**把本机选择器对齐到房间的 `mode`**，不要沿用自己进房前的模式。
- 改模式**不动当前曲目与进度**，换的只是「播完之后怎么走」。
- 退出房间时恢复自己原来的模式（与恢复个人播放现场同一套收尾，见 6.4）。

## 6. 客户端要做什么

### 6.1 镜像房间状态

收到 `room-playback` 后（以及此后每个本地节拍），把本地播放器对齐到房间状态：

```
目标进度 = livePosition(state, clockOffset)        # 见 6.2
曲目不同   → 用 track.sources 重建曲目并播放，再 seek 到目标进度，播放态照抄
同一首     → 先对齐播放态（play/pause），再按下面的阈值收拾进度偏差

|偏差| > 3s          → seek 过去，速率复位为 1
0.15s < |偏差| ≤ 3s  → rate = 1 - clamp(0.5 × 偏差, ±0.05)   # 比例速率微调
|偏差| ≤ 0.15s       → 速率复位为 1
暂停中               → 不做速率追赶，只在 |偏差| > 3s 时 seek
```

要点：

- **对齐必须由本地节拍驱动**（建议每 200ms 一次，纯本地计算、不发请求），
  不能只在收到广播时比一次；两次广播之间进度仍在走。
- 阈值**别按秒设**、也不要频繁 seek：seek 要重新缓冲。稳态一般能稳在 **±15~40ms**。
- 结束镜像时把 `playbackRate` 复位为 1。

### 6.2 校正时钟差

`room` / `room-playback` 都带 `serverNow`，用它算偏移：

```
clockOffset = serverNow - Date.now()      # 收到事件时更新
livePosition(state) = state.playing
  ? min(state.position + (Date.now() + clockOffset - state.positionAt) / 1000, state.duration)
  : state.position
```

单程估算里含着投递延迟（局域网也常有几十毫秒）。若要更准，可参照
`connect-protocol.md` 6.4 做往返测量（服务端 `POST /api/connect/time` 尚未实现）。

### 6.3 播不了就上报

监听本地播放失败：确定性失败 → `POST action unplayable { trackKey }`；
收到带 `skipReason: 'unplayable'` 的 `room-playback` 时给用户一个提示（两端都会收到这一帧）。
上报前先确认 `trackKey` 就是房间当前曲目，避免把预加载/切歌竞态的失败也算进去。

### 6.4 入房与退房的本地处理

- **入房**：立即按房间状态切歌（用户刚点过按钮，自动播放不会被浏览器拦），
  并**暂存自己的个人播放现场**（队列 / 下标 / 进度 / 播放态）。
- **退房 / 房间被解散**：恢复个人现场，并把 `playbackRate` 复位。
- **席位被接走**（`reason: 'seat_taken'`，见 7.8）：这一步**不是退房**。同样要恢复个人现场、
  把 `playbackRate` 复位，但房间状态（成员 / 队列 / 时长）要留着继续显示——本机只是改成旁观。
- **房间期间不要落盘个人播放现场**：否则房间队列会把「你自己原本在听什么」覆盖掉。
- **退出房间时，起播位置交给「恢复现场」的机制**，不要在恢复过程中先播再跳。
- **旁观设备不参与以上任何一步**（见 7.8）：它从没接管过播放器，也就没有「现场」要收、
  没有落盘要暂停。

## 7. 限制与边界

### 7.1 上限

- 人数上限由房间类型决定（见第 0 节）：`duo` **2 人**，`group` 预留 10 人。
  超出返回 `409 room_full`。
- 队列 **200 首**、payload **512 KB**。
- 一个**设备**只能在一个房间；同一**账号**在一个房间里只占**一个席位**
  （第二台设备不会占第二个名额，也不会被 `room_full` 挡住——它的 `join` 是顶替席位，见 7.8）。
- 席位记在 `members[].deviceId` 上（一个成员一条记录），所以**一个账号在一次房间里
  只有一台设备在出声**。这是刻意的：一起听是「你和对方听同一首歌」，不是「你的每台设备各放一遍」。

### 7.2 网关重启 / 刷新后回房

房间与队列都在内存里，重启即清空；本机刷新、进程被杀也一样要把「我在哪个房间」找回来
（参考实现把它记在本地）。

**但重连后不要盲目 `join`**：`join` 是「把席位接过来」，而上次可能是在**另一台设备**上听的。
正确做法是先 `GET /api/rooms/:code` 看 `mine`（见 4.5）：

| `preview.mine` | 含义 | 该做什么 |
|---|---|---|
| `null` | 本账号已不在房间里（席位过了宽限期、网关重启） | 可 `join` 回来；`404` 就本地收尾并提示「一起听已结束」 |
| 本机 `deviceId` | 席位本来就是本机的（掉线重连） | `join` 接回来接着放（幂等） |
| 我另一台设备的 `deviceId` | 一起听跟着那台走了 | **不要 `join`**，按旁观处理（7.8） |

本地存房间码时**连身份一起存**（本机当时是不是占着席位），能少问一次；但最终以 `preview.mine`
为准——本地那份可能已经过时（用户在另一台设备上把播放接走了）。

另外：席位在断线宽限期内还留着，本机重连时服务端（`onDeviceOnline`）会自动补推房间快照，
**无需重新 join**；`join` 只在「席位可能已经不属于本机」时才需要。

### 7.3 断线宽限（10 分钟）

**在线与否只看那条 SSE 连接**，但成员**席位与连接解耦**：

- SSE 断开 → 成员标记 `online: false`，**席位保留 10 分钟**；
- 期间以**同一 `deviceId`** 重连（SSE 的 `hello`）→ 服务端自动复用席位并补推房间快照，
  **无需重新 join**；
- 10 分钟仍未回来 → 移除席位；房间空了即销毁。

注意这期间席位是**占着**的：双人房里另一方这 10 分钟内叫不到新人——这是刻意的
（双人房是「固定的你和我」，重连即恢复，也避免房间被顶掉）。

### 7.4 结束 / 解散

- `duo`：任一成员都能结束（人人平权）。**一个人结束，房间就散了**——双人房里
  「退出但让房间留着」没有意义（剩下一个人也一起听不成）。
  所以客户端在双人房**只提供「结束」一个动作**，不要给「退出」。
- `group`：只有房主能解散（`403 not_room_owner`）。

服务端把关闭广播（`room: null`）发给**所有成员账号下的设备**。客户端据此可确认「是谁结束的」：

| 本机是否发起 | 客户端看到什么 | 应提示 |
|---|---|---|
| 是 | 本地已经先收尾，`room: null` 到达时已不在房间 | 自己给一句「已结束一起听」 |
| 否 | 在房间内收到 `room: null` | `duo` →「对方结束了一起听」；`group` →「房主结束了一起听」 |

被结束的一方收到后应**恢复自己的播放现场**（与主动退出同一套收尾）。

第三种 `room: null` 带 `reason: 'seat_taken'`：席位被同一账号的另一台设备接走了（见 7.8）。
这时**房间并没有散**，只是播放换了设备，所以客户端**不要**按「房间没了」收尾——那会让界面退回
「创建 / 加入」的样子，看着像一起听被谁结束了。正确做法是降级为旁观：房间继续显示，
播放器还给用户自己的队列。提示语也要说成「已转移到「X」」，而不是「对方结束了一起听」——
两者的用户动作完全不同。

判据集中在服务端的 `roomPolicy(kind)`（以及播放动作的 `canAct()`），
不在别处散落类型判断——将来调整权限只改那一处，协议与客户端不用动。

### 7.5 一起听时长（`duo`）

同一个统计有两个读数，**必须分别展示、分别标清楚**：

| 字段 | 含义 | 范围 |
|---|---|---|
| `togetherSessionSeconds` | **本次**：这一次房间听了多久 | 从两人凑齐那刻起算；换人 / 重新开房即归零 |
| `togetherSeconds` | **累计**：这两个人一共一起听过多久 | 跨房间、跨会话，落在 `together_durations` 表里 |

为什么要分两个：只给一个"累计"的话，用户没法回答"我们这次听了多久"——那个数会把过去几次
一起听都算进来。两者是包含关系：`togetherSeconds ≥ togetherSessionSeconds`。

累计值刻意按「用户对」记账而不是挂在房间上：房间是易失的内存对象，而这个数得活过房间本身。

计时口径（`duo` 专属，`group` 未实现）：

- **两人都在房间里就走表**，暂停、发呆、拖进度都算（不是"播放中"的时长）。
- 只有一个人的时候不走表——还不知道对方是谁，也就谈不上"一起听"。
- 与**在线状态无关**：断线后席位仍保留 10 分钟（见 7.3），那段时间两人依然在一起听。
- 一方退出（或被宽限到期移出）→ 停表；房间解散 → 停表并结算。

落库节奏：**每 60 秒兜一次 + 停表时结算一次**（只有累计值需要落库，本次值随房间生灭）。
房间是内存里的，只靠"结束时结算"会让一个开了一整天的房间在网关重启时丢掉全部时长；
每分钟兜底把最坏损失压到 1 分钟。

服务端落的是**两张表、两套账**：

| 表 | 内容 | 主键 | 写失败时 |
|---|---|---|---|
| `together_durations` | 累计值（一对用户一行） | `(user_a, user_b)` | 放回待落库表**重试** |
| `together_sessions` | 明细（一次「房间 + 用户对」一行） | `(room_code, user_a, user_b)` | 只记日志，**不重试** |

明细表是为了以后能做历史/统计（「哪天一起听的」「每次多久」）。它与累计值互不影响，
**不想要了直接 `drop table together_sessions`** 即可，累计值一点不受影响。

明细里同一对人**在同一个房间**反复进出（掉线重连、中途退出又回来）算同一行；换了人则是新的一行。

客户端怎么用这三个字段：

```
# 收到 room 事件时，连同 serverNow 一起存下
session  = room.togetherSessionSeconds   # 本次
total    = room.togetherSeconds          # 累计
counting = room.togetherCounting

# 走表时自己往前推，否则读数要等下一次事件才跳：
走了多久 = counting ? max(0, (Date.now() + clockOffset - serverNow) / 1000) : 0
本次显示 = session + 走了多久
累计显示 = total + 走了多久
```

- 三个字段在**不满员时分别是 0 / 0 / false**（不知道对方是谁），客户端不要在此时展示这块。
- 单位是**秒**（整数，向下取整），与 `position` 同单位；格式化请自行处理成「X 小时 Y 分钟」。

### 7.6 一起听总览（账户中心）

```
GET /api/rooms/overview
→ {
    "totalSeconds": 4200,
    "partnerCount": 2,
    "partners": [
      { "userId": "2", "nickname": "小明", "avatar": null,
        "seconds": 3600, "lastAt": "2026-10-13T05:20:11.000Z" }
    ],
    "sessionCount": 2
  }
```

- 只返回**当前登录用户**的数据，按累计时长倒序。
- `totalSeconds` 是与所有人累计之和；`partners[].lastAt` 是最近一次一起听的时间
  （取自累计行的更新时间，也就是最后一次落库的时刻）。
- `sessionCount` 来自明细表；**那张表随时可能被 drop**（见 7.5），那时这里是 `null`，
  客户端应把这一项整个隐藏，而不是显示成 0。
- 时长与伙伴来自可靠的累计表，明细表存在与否都不影响这两项。

### 7.7 某位好友的每次明细（点开好友看）

```
GET /api/rooms/overview/:partnerId
→ {
    "partner": { "userId": "2", "nickname": "小明", "avatar": null },
    "totalSeconds": 4200,
    "sessionCount": 2,
    "sessions": [
      { "startedAt": "2026-10-13T04:20:11.000Z", "seconds": 3600 },
      { "startedAt": "2026-10-06T12:00:00.000Z", "seconds": 600 }
    ]
  }
```

- 只返回**当前用户与这位伙伴**之间的数据，谁看谁的都一样（用户对已规范化）。
- `sessions` 按 `startedAt` **倒序**（最近的在最前），最多返回 200 条；
  若 `sessions.length < sessionCount` 表示被截断，界面补一句「仅显示最近 N 次」。
- 明细表被 drop 时，`sessionCount` 与 `sessions` 都是 `null` —— 客户端要说清
  「只有累计可用」，而不是显示成"没一起听过"。
- 伙伴不存在（已被删除）返回 `404 user_not_found`。

### 7.8 同一账号的第二台设备：旁观与「转移到本机」

一个账号只有一个席位（7.1），但**账号里的每台设备都会收到房间事件**。于是每台设备有两种身份，
由 `members[].me` 区分（**别用账号 id 或成员条数去猜**）：

| 身份 | 判据 | 本地播放器 | 界面 |
|---|---|---|---|
| **席位设备**（在放的那台） | `members` 里有一条 `me: true` | 镜像房间状态，传输控制走 action（见第 6 节） | 正常的双人房界面 |
| **旁观**（同账号的另一台） | 没有任何 `me: true`，但有 `mine: true` | **一个字节都不碰**：不镜像、不捕获/恢复个人现场、不落盘暂停、不发 action | 「正在「X」上播放，本机没在放」+ **转移到本机** |

旁观设备要做与不要做的事：

- **不要**镜像播放：歌是在另一台设备上响的。它自己的播放器就是它自己的（可以正常听别的歌）。
- **不要**上报 `ended` / `unplayable`，**不要**发任何 action（服务端会 `404 room_not_found`）。
- **不要**暂停个人播放现场的落盘：它压根没接管过播放器。
- 「结束一起听」也不该出现在它上面（解散的鉴权是席位设备级的）。
- 时长、成员、谁在线这些**照常显示**——旁观者看到的是一份只读的房间快照。

> 只有一处例外：**刚被接走席位的那台**（下面的降级）入房时捕获过个人现场，降级时要把它恢复回来
> 并放开落盘——那是它作为「席位设备」的收尾；收完尾之后就按旁观这一套走。

**转移到本机**：对房间码再发一次 `join`（第 4.2 节）。服务端把席位挪到本机，并连推三帧：

```
本机      ──join──▶ 服务端（席位换到本机）──room + room-playback──────────▶ 本机开始镜像播放
                          ├──room: null, reason: "seat_taken" ────────▶ 原来那台：降级为旁观
                          └──room（全量快照，me: false / mine: true）──▶ 原来那台：继续显示这个房间
```

原来那台收到 `reason: 'seat_taken'` 后要做的是**降级为旁观**，三步：

1. 停止镜像、把 `playbackRate` 复位、恢复自己的个人播放现场——播放器不再归房间管；
2. **保留**房间码与房间状态（成员 / 队列 / 时长），界面继续显示这个房间，按上表写成
   「正在「X」上播放，本机没在放」+「转移到本机」；
3. 把随后那份快照照常收下：它正是「继续显示」所需的数据来源（那一帧里本机 `me: false`、
   `mine: true`，身份天然就是旁观）。**不要**把它当「不认识」丢掉，也**不要**本地清空房间。

反面做法（曾经踩过）：把 `seat_taken` 当成「房间没了」那样收尾，再用一个「我刚出局」的标记
把紧随其后的那份快照拒掉。结果是客户端表现为「一起听没了」——面板退回「创建 / 加入」的样子，
非刷新（重连后服务端补推快照）不恢复——而房间其实还开着，两个人还在里面。

冷启动 / 刷新时判断自己是哪种身份，走 7.2 的 `preview.mine` 流程。

## 8. 错误码

| HTTP | code | 场景 | 该怎么办 |
|---|---|---|---|
| 400 | `invalid_device_id` | `deviceId` 为空或超过 64 字符 | 修 bug |
| 400 | `invalid_index` / `invalid_position` / `invalid_track` | 参数不合法 | 修 bug |
| 400 | `unknown_action` | action 不在白名单 | 修 bug |
| 400 | `invalid_mode` | `setMode` 的 `mode` 不是四个取值之一 | 修 bug |
| 400 | `queue_full` / `queue_too_large` | 队列超限 | 提示用户 |
| 400 | `room_empty` | 空房间执行了 `play` | 先 `setQueue` |
| 400 | `room_kind_unsupported` | 创建了尚未开放的房间类型（`group`） | 隐藏该入口 |
| 409 | `room_full` | 房间已满 | 提示「房间已满」 |
| 409 | `duplicate_track` | `add` 了一首队列里已有的歌 | 忽略即可 |
| 403 | `not_a_member` | 不是该房间成员 | 修 bug / 重新入房 |
| 403 | `not_room_owner` | 非房主执行管理动作（`group` 房的解散/踢人） | 隐藏该入口 |
| 404 | `room_not_found` | 房间不存在（已解散/网关重启） | 本地收尾，提示已结束 |
| 401 | `unauthorized` | 未登录 / 会话过期 | 跳登录 |

# 多设备播放协议

面向客户端开发者。本文描述「多设备管理与控制」——同一账号下的多台设备互相可见，任意一台都能控制另一台播放，或把播放整体搬过去。

- 服务端实现：`gateway/src/services/connect.ts`、`gateway/src/routes/connect.ts`
- 参考客户端：`web/src/stores/connect.ts`、`web/src/components/DevicePicker.vue`
- **播放本身**（取流、音质、歌词、音乐库）与本文无关，仍见 `client-android/API.md`

## 1. 它是什么 / 不是什么

**是**：一套「谁在放歌、放到哪儿了、让谁接着放」的控制协议。设备之间互相可见，可以互相遥控，也可以把整条播放队列连进度一起交接。

**不是**：

- 不是把音频从一台设备推给另一台。音频永远由**真正出声的那台设备自己**去取（走 `/api/stream` 或直连平台 CDN），本文这套协议**一个音频字节都不传**。
- 不是云端播放状态同步。设备状态只在内存里，网关重启即清空（设备重连后重新上报）。
- 不是播放历史/断点续播。那部分在音乐库里（`/api/history`），是另一回事。

---

## 2. 控制面与数据面

理解这条界限，后面的一切都顺：

| | 控制面（本文） | 数据面（与本文无关） |
|---|---|---|
| 通道 | SSE 长连接 + 两个 POST | `/api/stream` 或直连 CDN |
| 内容 | 设备列表、播放状态、控制指令 | 音频字节 |
| 量级 | 一次上报约 200–400 字节，且**只在状态变化时发生** | 128 kbps ~ 1000 kbps |
| 谁承担 | 所有在线设备 | 只有正在出声的那台 |

**控制端不要为了"控制"去拉音频。** 一台设备遥控另一台播放时，控制侧常态下**不产生任何上行请求**（只有那条 SSE 连接）—— 这正是这套设计的意义。

## 3. 设备身份

每个「播放实例」需要一个 `deviceId`：

| 要求 | 说明 |
|---|---|
| 长度 | 非空，≤ 64 字符（超了返回 `400 invalid_device_id`） |
| 唯一性 | 同一账号内唯一即可，服务端不校验格式，也不生成 |
| 生成时机 | 客户端首次运行时生成随机串并持久化 |
| 粒度 | 一个**播放实例**一个。Android 一台设备一个；Web 因为播放器活在页面里，是**每个标签页一个** |

持久化的意义：应用重启后沿用同一个 id，这台设备就是"同一台"；换了 id 会被当作新设备（旧设备在连接断开时已从列表消失，所以不会残留幽灵，只是名字要重新起）。

**同一个 `deviceId` 重复连接**：服务端会顶掉旧连接（新的赢）。这既是刷新页面/断线重连的正确行为，也意味着**不要**让两台真实设备共用一个 id——它们会互相踢下线。

## 4. 接口总览

所有接口都在网关 `/api` 前缀下，鉴权与会话同一套：**HttpOnly Cookie `sakura_session`**（见 `API.md` 第 1.1 节）。

| 方法 | 路径 | 作用 |
|---|---|---|
| GET | `/api/connect/events` | 设备长连接（SSE），建立即上线、断开即下线 |
| POST | `/api/connect/state` | 上报本机播放状态 |
| POST | `/api/connect/command` | 给某台设备下发控制指令 |
| POST | `/api/connect/time` | 往返时钟测量，返回 `{ ok, now }`（见 6.4） |

未登录一律 `401`。

## 5. 设备长连接（SSE）

### 5.1 建立

```
GET /api/connect/events?deviceId=<id>&name=<设备名>&kind=<web|android|windows>
```

| 参数 | 必填 | 说明 |
|---|---|---|
| `deviceId` | 是 | 见第 3 节 |
| `name` | 否 | 展示用名称，≤ 40 字符。留空由服务端按 `kind` 给个默认名 |
| `kind` | 否 | `android` / `windows`，**其它值一律当 `web`**（用于界面挑图标） |

响应头：

```
Content-Type: text/event-stream; charset=utf-8
Cache-Control: no-cache, no-transform
Connection: keep-alive
X-Accel-Buffering: no
```

帧格式就是标准 SSE：

```
event: <事件名>
data: <JSON>

```

### 5.2 事件

#### `hello` —— 建连后立即下发，只有一次

```json
{
  "deviceId": "自身设备 id",
  "devices": [ /* DeviceView[]，已包含自己 */ ]
}
```

#### `devices` —— 设备列表变化，全量推送

任何设备**上线、下线、上报状态**之后都会推给该账号下的所有设备（包括触发者自己）。

```json
{ "devices": [ /* DeviceView[]，全量，不是增量 */ ] }
```

`DeviceView`：

```json
{
  "deviceId": "abc123",
  "name": "客厅的电脑",
  "kind": "web",
  "online": true,
  "state": {
    "track": {
      "key": "netease:186016",
      "title": "晴天",
      "artists": "周杰伦",
      "album": "叶惠美",
      "cover": "https://…",
      "durationMs": 269000,
      "activePlatform": "netease",
      "sources": [{ "platform": "netease", "id": "186016" }]
    },
    "playing": true,
    "position": 12.4,
    "positionAt": 1758600000000,
    "duration": 269,
    "volume": 0.8,
    "quality": "high",
    "outputLatencyMs": 0,
    "rate": 1,
    "queueLength": 3,
    "playMode": "all"
  }
}
```

- `online` 恒为 `true`：离线设备会被**直接从列表里摘掉**，不保留墓碑。所以「在线设备」= 列表里的元素。
- `state` 为 `null` 表示这台设备刚连上、还没上报过状态。
- `state.track` 为 `null` 表示没在放歌（设备可能空闲，也可能在播但曲目未知）。
- 全量推送意味着**收到相同列表是正常的**，客户端做去重/浅比较可以省掉无谓重绘。

#### `command` —— 发给本设备的控制指令

```json
{ "from": "发起方 deviceId", "action": "seek", "payload": { "position": 42 } }
```

`from` 很重要：**接管的回程要用它当收件人**（见第 8 节）。

### 5.3 心跳与重连

- 服务端每 **25 秒**发一行注释帧 `: ping`（不产生任何事件）。用途是穿过 Nginx 之类的中间代理、防止连接被判空闲。
- 客户端**不需要**回应心跳。建议：若 60 秒内既没收到事件也没收到心跳，判定连接已死并重连。
- 重连用指数退避（1s 起、上限 30s 左右即可）。
- **`401` 时不要重连**：那说明会话过期或未登录，重试只会一直失败。等登录成功后重新建连。
- 服务端**不支持 `Last-Event-ID` 续传**——不需要：重连后的 `hello` 就是一份完整快照。

### 5.4 在线判定：只看这条连接

**在线的定义就是这条 SSE 连接还活着**，没有第二个判据。客户端**不要**用状态上报来"证明在线" —— 那等于同时维护两套在线判定，迟早互相打架。

不同情况下服务端发现"断了"的时机差别很大：

| 设备发生了什么 | 服务端多久发现 |
|---|---|
| 正常退出、关页面、进程被强杀 | **秒级** —— 对端（或它的操作系统）会发 FIN/RST |
| 网络中断（休眠、拔网线、WiFi 切 4G） | **几十秒 ~ 十几分钟** —— 没有 FIN，只能等 TCP 重传超时 |

第二行是 TCP 的固有性质，不是协议缺陷：SSE 是单向的，服务端只能写，而写成功只代表数据进了本地内核缓冲区，收不到 ACK 时它无法立刻区分「对端变了」和「网络卡了一下」。服务端每 25 秒的 `: ping` 写操作本身就在做这个探测，所以死连接**最终一定会被清掉**，不会永久残留。

于是列表里可能短暂存在「已经死掉、但还显示在线」的设备。**不要为此加应用层心跳回包** —— 那点精度用 7.4 的送达确认就能覆盖，而且判据更可靠。

客户端**不需要**发送任何"我下线了"的消息；正常退出时关掉连接即可。

### 5.5 手工验证

```bash
curl -N -H "Cookie: sakura_session=<你的会话>" \
  "http://127.0.0.1:8787/api/connect/events?deviceId=curl-test&name=命令行&kind=windows"
```

另开一个终端上报状态，就能在上面的输出里看到 `devices` 事件。

## 6. 上报播放状态

```
POST /api/connect/state
Content-Type: application/json

{
  "deviceId": "abc123",
  "state": {
    "track": { …同上… },
    "playing": true,
    "position": 12.4,
    "duration": 269,
    "volume": 0.8,
    "quality": "high",
    "queueLength": 3
  }
}
```

响应：

```json
{ "ok": true }
```

`ok` 为 `false` 表示**这台设备当前不在线**（还没建 SSE，或连接已断）。这**不是错误**：不要重试、不要报错给用户。它会在 SSE 重连后由补报纠正（见 6.5）。

### 6.1 字段与夹取规则

| 字段 | 类型 | 说明 | 服务端处理 |
|---|---|---|---|
| `deviceId` | string | 必须与 SSE 用的**完全一致** | 不在表里 → `ok:false` |
| `track` | object \| null | 当前曲目摘要 | `key` 为空视为没有曲目 |
| `track.key` | string | 曲目唯一键（如 `netease:186016`） | ≤ 200 字符 |
| `track.title` | string | 标题 | ≤ 200 |
| `track.artists` | string | **已拼好的字符串**（如 `周杰伦 / 费玉清`），**不是数组** | ≤ 300 |
| `track.album` | string | 专辑名 | ≤ 200 |
| `track.cover` | string \| null | 封面 URL | ≤ 1000，空串记 `null` |
| `track.durationMs` | number | 毫秒 | 0 ~ 86400000 |
| `track.activePlatform` | string | 本机**实际在用**的音源平台（`netease` / `qq`）。跟随端照抄它，两端才拿到同一份编码 | ≤ 20；空串 = 未知 |
| `track.sources` | array | **取流坐标**：`{ platform, id, mid?, numericId? }` | 最多 4 条；`platform` 与 `id` 为空的项丢弃 |
| `playing` | boolean | **严格等于 `true`** 才算在播 | 其它值一律 `false` |
| `position` | number | 秒，当前进度 | 0 ~ `duration`（`duration` 为 0 时上限 86400） |
| `duration` | number | 秒，总时长 | 0 ~ 86400 |
| `volume` | number | 0 ~ 1 | 夹取 |
| `quality` | string | 音质档位标识（跟随端据此锁定同一音质），取值见播放 API 的档位枚举：`standard`/`high`/`lossless`/`hires`/`spatial`/`master`/`surround` | ≤ 20 |
| `outputLatencyMs` | number | 本机音频输出延迟估算（毫秒）。`0` = 未测出，跟随端不作补偿 | 0 ~ 5000，四舍五入到整数 |
| `rate` | number | 本机播放速率（为追平微调时不是 1），诊断用 | 夹取到 0.5 ~ 2 |
| `queueLength` | number | 队列条数，仅供显示 | 0 ~ 10000，四舍五入到整数 |
| `playMode` | string \| 省略 | 播放模式：`order` / `all` / `one` / `shuffle`（见 7.6） | 认不出的取值当作没报（`undefined`） |
| `following` | string \| 省略 | 本机正在跟随谁（对端 `deviceId`） | ≤ 64 字符；空串记作省略 |

字符串按**字符**截断而不是报错——宁可少显示几个字，也不要让一条状态把整台设备卡住。

### 6.2 不要传 `positionAt`

`positionAt`（服务端盖章的上报时刻）由服务端写入，客户端传了也会被覆盖。

原因：各设备系统时钟不会一致。若让客户端自带时间戳，控制端的进度条会整体偏移 —— 差几秒看不出来，差几分钟就很荒唐。

### 6.3 上报时机：只在变化时上报

| 时机 | 说明 |
|---|---|
| 播放 / 暂停、换歌、队列长度变化 | **立即**上报 |
| 播放模式变化 | **立即**上报（控制端的面板据此高亮） |
| 拖动进度条（播放中与暂停中都要） | **立即**上报 |
| 执行完远程指令 | **立即**补报 |
| 播放进度 | **完全不报** —— 控制端按 `positionAt` 自己推算（见 6.4） |

**协议不要求任何周期性上报。** 一台正常播放的设备，上行请求数应该是 **0**。

在线与否由 SSE 连接本身保证，与上报无关 —— 不上报状态不会被判定为离线。

不要按"每次 `position` 变化都上报"实现：`position` 每 250ms 变一次，那会变成持续的请求洪流，而进度本来就该由接收方推算。

代价是失去了"周期对表"的自愈能力，所以需要配两样保险（见 6.5）：

- **失败重试** —— 丢一次没有周期上报来纠正，会一直错到用户下一次操作；
- **本地偏差检测** —— 兜住两类事件驱动看不见的情况：播放中拖动进度条（`currentTime` 跳变但不产生状态变化）、音频缓冲卡顿（进度停住但仍在"播放"）。

参考实现的实际频率：

| 设备状态 | 请求频率 |
|---|---|
| 正在播放（无操作） | **0** |
| 暂停 / 空闲 | 0 |
| 页面 / 进程已关闭 | 0（SSE 断开，设备下线） |
| 用户拖了进度、或音频卡顿 | 补报一次，最多每 5 秒一次 |

### 6.4 控制端如何显示进度

```ts
// 播放中：从上报时刻起本地推算，并掐住上界
const elapsed = (Date.now() - state.positionAt) / 1000;
let position = Math.max(0, state.position + elapsed);
if (state.duration > 0) position = Math.min(position, state.duration);
// 暂停：直接用 state.position
```

两个要点：

- **必须掐上界**：没有周期上报之后，控制端可能独自推算很久，播完那一刻位置会越过曲长。
- 误差来自「控制端时钟」与「服务端 `positionAt`」的差值。它是**固定偏移、不会随时间累积**（每次上报都重新对表）。

**怎么把时钟差校正得足够准。** `hello` / `devices` 里带着 `serverNow`，但那是**单程**估算 —— 投递延迟会整体算进偏移里，误差就是一个单程网络延迟（局域网也常有几十毫秒）。而跟随同步恰恰卡在这个量级上，所以要走 `POST /api/connect/time` 做往返测量：

```
发出前记 sentAt → POST /api/connect/time → 收到后记 receivedAt
rtt    = receivedAt - sentAt
offset = now - (sentAt + receivedAt) / 2      # 假定上下行对称
```

建议连采 5 次、**取 RTT 最小的一条**（最小 RTT 那次最不可能被排队延迟污染），把误差压到 RTT/2；每 60 秒左右重新对一次，抵消晶振漂移。此后一切推算都该用校正后的「服务端时间」（即 `Date.now() + offset`）。

### 6.5 兜底：重试与偏差检测

**失败重试。** 上报失败必须退避重试（如 0.8s、2.4s，共 2~3 次）。注意区分：

- 网络异常、`5xx` → **值得重试**；
- `4xx`（会话过期、参数不合法）→ 重试没用，直接放弃；
- 响应 `ok: false` → **不是失败**，只是设备不在线，不要重试。

另外建议在 **SSE 重连成功后主动补报一次**（重连意味着中间断过，本地状态可能与服务端的不一致）。

**偏差检测。** 本地起一个轻量定时器（如每秒一次，不产生网络请求），把「实际进度」与「上次上报位置 + 本地已流逝时间」比一比：

```
expected = 上次上报的 position + (本地单调时间 - 上次上报时刻) / 1000
偏差 = 实际 position - expected
```

偏差绝对值超过阈值（约 1.5 秒）就补报一次。要点：

- 时间基准用**单调时钟**（`performance.now()` 一类），不要用挂钟 —— 系统校时、睡眠唤醒会让挂钟跳变，会被误判成"用户拖了进度"。
- 卡顿时偏差会持续存在，**必须加冷却**（如 5 秒），否则补报会比原来的周期上报还频繁。
- 只在**播放中**做检测：暂停时进度不会自己走，那一路由"暂停状态下的拖动"单独覆盖。

## 7. 下发控制指令

```
POST /api/connect/command
Content-Type: application/json

{
  "deviceId": "发起方自己的 id",
  "target": "目标设备 id",
  "action": "seek",
  "payload": { "position": 42 }
}
```

响应 `{ "ok": true }`。指令是**异步**的：`ok` 只代表已经转发到目标设备的连接上，不代表目标已经执行。

`deviceId` 填自己：服务端用它填 `command` 事件的 `from`。**漏填的后果是接管功能失效**（对方不知道把队列交给谁）。

### 7.1 action 全表

| action | 语义 | payload |
|---|---|---|
| `play` | 开始 / 继续播放 | 可带队列（见下）；不带就是 resume |
| `pause` | 暂停 | 无 |
| `toggle` | 播放 ⇄ 暂停 | 无 |
| `next` | 下一首 | 无 |
| `prev` | 上一首 | 无 |
| `seek` | 跳到第 N 秒 | `{ "position": 42 }` |
| `volume` | 调那台设备的音量 | `{ "volume": 0.6 }` |
| `follow` | 让那台设备跟随你播放 | 无（发起方就是它要跟随的对象） |
| `unfollow` | 撤销上一条 | 无 |
| `transfer` | 接管播放：载入队列并定位 | `{ "queue": [...], "index": 0, "position": 12.4 }` |
| `release` | 把队列交出去并停下自己 | 无（对端随后以 `transfer` 回传） |
| `mode` | 切换那台设备的播放模式 | `{ "mode": "shuffle" }` |
| `playAt` | 播放它播放列表里的第 N 首 | `{ "index": 3 }` |
| `remove` | 从它播放列表里移除第 N 首 | `{ "index": 3 }` |
| `add` | 往它播放列表末尾追加一首 | `{ "track": { … } }` |
| `queue` | 要一份它的播放列表快照 | 无 |
| `queueState` | `queue` 的应答（由被请求的那台回传） | `{ "queue": [...], "index": 0 }` |

不在表里的 action 一律 `400 unknown_action` —— 服务端是白名单转发，不是透传。

### 7.2 payload

```json
{
  "queue": [ /* UnifiedTrack[]，见第 9 节 */ ],
  "index": 0,
  "position": 12.4
}
```

- `queue` 由网关**不透明透传**：它不解析、不校验结构，只检查总大小 ≤ **512 KB**（超了 `400 payload_too_large`）。
- `index` 是要播第几首（从 0 开始），`position` 是从那一首的第几秒开始。
- `position > 0.5` 才值得 seek，太小的偏移可以忽略（避免"刚播就跳"的观感）。

注意 `volume` 调的是**那台设备**的音量，不是播放内容的属性：同一份播放状态在不同设备上可以有不同的音量，这也是跟随时唯一不该同步的东西（每个人的环境不同）。

### 7.3 收到指令后要做的事

1. 用与本地点击**完全相同**的播放器方法执行（不要给"被遥控"单开一条路径，两条路会慢慢长歪）。
2. 执行完**立刻补报一次状态**（`POST /api/connect/state`）。

第 2 条不只是"让进度刷新得快一点"——**控制端就是靠它来确认指令送达的**（见 7.4）。漏掉的话，你会在别人眼里变成一个"总是没响应"的设备。

### 7.4 送达确认（控制端必做）

网关返回的 `ok: true` 只代表"已经写进那条连接"，**不代表对方还在**。网络中断的设备仍然挂在列表里（TCP 要过一会儿才发现，见 5.4），这时指令会石沉大海。

判据现成：**被遥控的设备执行完指令会立刻补报状态**（7.3 第 2 条）。所以控制端只要：

```
发指令前：记下目标设备当前的 state.positionAt
发指令后：等 3~5 秒
  如果目标还在列表里，且它的 positionAt 变大了  → 送达
  如果目标已从列表消失                          → 已离线
  如果 positionAt 没变                          → 提示「该设备可能没有响应」
```

这个判据比心跳可靠：它验证的不是"连接还在"，而是"对方真的响应了"。

两个注意点：

- `release` 是一个往返（见第 8 节），确认状态交给回程的 `transfer` 那一步，不要在 `release` 之后就下结论。
- 提示语气要留余地（"可能已离线"）。如果对方执行了指令但状态上报恰好失败，也会被误判。

### 7.5 跟随播放

「跟随」= 本机把自己当成另一台设备的镜像输出：曲目、播放态、进度都跟着它走。

**跟随是双向可选的**，两个方向走的路子完全不同：

| 方向 | 怎么做 | 走协议吗 |
|---|---|---|
| 我跟随它 | 本机把自己的 `following` 设成对方 deviceId，然后照着它的状态对 | **不走** |
| 它跟随我 | 发一条 `follow` 指令过去，由**它自己**把 `following` 设成本机 | **走**（`follow` / `unfollow`） |

第一个方向不需要协议：目标设备的状态本来就通过 `devices` 事件广播过来，本机照着对就行：

```
收到 devices 事件、或本地节拍到点（且本机正在跟随时）
  ├─ 曲目不同   → 按 track.activePlatform / quality 锁定音源，用 track.sources 重建曲目并播放，
  │               再 seek 到 livePosition(target)，播放态照抄
  ├─ 同一首歌   → 先对齐播放态，再按上面的比例控制收拾进度偏差
  └─ 目标已下线 → 结束跟随（先给一段宽限期，见下）
```

第二个方向必须走协议：**「让谁跟随谁」这个意图没法靠广播推断出来**，得有人明确要求一次。注意请求方不因此获得任何持久权限 —— 跟不跟由被请求方决定，它随时可以自己停掉。

**`following` 字段是双向可见的关键**：被跟随的一方正是靠它确认「对方到底跟上了没有」。光看两台都在放同一首歌，分不清是同步播放还是各放各的。所以它一变就要立刻上报。

三个要点：

- **`track.sources` 是前提**：没有它就无法解析播放地址，跟随端只能干看着（见 6.1）。
- **`track.activePlatform` + `quality` 是前提之二**：两端各挑各的音源会拿到不同编码的波形，进度对得再齐也叠不出「一个声音」。重播曲目之前先按这两个字段把音源锁死。
- **它是收敛的**：同步完本机自己也会上报，下一轮比对就一致了，不会来回弹。
- **跟一台「正在跟别人」的设备 = 跟它跟随的那台**：`following` 是单值，链式关系（B 跟 C、本机跟 B）里的中间那几台都只是镜像。照着 B 对，等于把 B 的残差再叠一层，源头换歌时还要多等一次转发。所以建立跟随关系时应当沿目标的 `state.following` 一路走到链尾那台；只有在下游不在设备列表里（离线 / 还没入册）或下游已经在来路上出现过（成环、指回本机）时才停在前一台。这是纯本地决策，不用发任何指令 —— 而它一旦成立，`following` 就该改成源头那台的 id 并上报，别让广播里的关系和实际对的对象不一致。
- **务必校正时钟差**：推算用的是「本机时钟 − 服务端盖的 `positionAt`」，两台机器的时钟差多少，推算就整体偏多少，**而且永远不会自愈**。别只用 `devices` / `hello` 里的 `serverNow`（那是单程估算），按 6.4 做往返测量。
- **目标缺席要给宽限期**：设备重连时会在设备列表里缺席一小段（旧连接被摘除、新连接还没入册）。一帧看不见就清掉跟随关系的话，一次毫秒级的瞬断就能把同步永久打断，而且对端回来也不会自动恢复。建议先记下缺席起点，超过 10~15 秒才认定下线。

建议实现成**只读镜像**（跟随期间本机的传输控制不转发给对方）：这样不必去拦播放条上的每个按钮，用户想自己控制时先停止跟随即可，语义清楚。

#### 把偏差压到最小

按代价从低到高：

| 手段 | 消掉的是哪一块 |
|---|---|
| 往返测量校正时钟差（6.4） | 最大的一块：两机时钟差，以及单程估算里的投递延迟 |
| 小偏差用**比例速率微调**（`playbackRate = 1 ± 5%`） | 「seek 后重新缓冲」的卡顿；±5% 在 `preservesPitch` 下只是轻微变速 |
| 大偏差才 seek | 唯一能一次性清掉大偏差的手段，但要重新缓冲，所以是最后手段 |
| 用 `outputLatencyMs` 对齐**输出**而非解码位置 | 两端音频输出延迟之差（同类设备也可能差几十毫秒） |

**对齐必须由本地节拍驱动，不能只靠广播。** 广播是稀疏的（只在状态变化时来），两次广播之间目标设备的进度仍在走 —— 只在事件到来时比一次的话，跟随端会以自己的时钟自由漂移，等下一次广播才被拽回来，而那一刻的偏差正好又听得出来。参考实现每 200ms 跑一次纯本地比对，不产生任何请求：

```
偏差 = 本机进度 - 目标此刻的进度          # 目标进度按 6.4 推算

|偏差| > 150ms        → seek 过去，速率复位为 1
5ms < |偏差| ≤ 150ms  → rate = 1 - clamp(0.5 × 偏差, ±0.05)
|偏差| ≤ 5ms（死区）   → 速率复位为 1
暂停中                → 不做速率追赶，只在 |偏差| > 150ms 时 seek
```

三个要点：

- **阈值别按秒设**。`|偏差| > 3 秒才 seek` 意味着稳态就可能停在几百毫秒 —— 那是同房间绝对听得出来的量级。150ms 以内一律交给速率微调，那才是听不出来的手段。
- **死区是必须的**：没有死区，速率会在 1 附近来回抖。
- **暂停时追赶没有意义**：速率只对「正在走的进度」起作用，暂停中改速率不会让进度靠近，反而会在恢复播放的瞬间带着一个莫名其妙的倍速。

**别指望零延迟。** 各端独立缓冲、独立解码，又没有共享时钟。往返对表 + 比例控制一般能稳在 **±15~40 毫秒**；要进到 20 毫秒以内乃至亚毫秒，得靠硬件时钟同步（Dante / AES67 / PTP 那一类），不在这套东西的范畴。

**同房间的一条物理限制。** 两个扬声器位置不同，声波叠加必然产生梳状滤波（音染）—— 这跟同步得多准无关。同步能消除的是**回声感**（先后到达），消除不了音染。所以同房间想要更好的听感，靠的是把这几个设备**摆近**，而不是把精度再压几个毫秒。

还有两个容易忘的收尾：结束跟随时、以及连接断开时，都要把 `playbackRate` 复位为 1，否则会留下一个"莫名其妙快/慢几个百分点"的播放器。

### 7.6 遥控播放模式与播放列表

**播放模式**是目标设备自己的状态，走一条普通指令：

```json
POST /api/connect/command
{ "deviceId": "本机", "target": "对方", "action": "mode", "payload": { "mode": "shuffle" } }
```

对方用本地的「设置播放模式」方法执行，然后立刻补报；`state.playMode` 随之更新。四种取值与「一首播完往哪走」的关系：

| 取值 | 播完一首后 |
|---|---|
| `order` | 下一首；到队尾停下 |
| `all` | 下一首；到队尾回到第一首 |
| `one` | 原地重播当前这首 |
| `shuffle` | 随机跳到另一首 |

`state.playMode` 缺省（老客户端没报）时，控制端应显示为**未知**，而不是假称 `order`。

**播放列表**体积大（每首带取流坐标），不放进每次变化都要全量广播的 `devices` 事件，改按需索取：

```
控制端 ── command { action: "queue" } ──▶ 对方
控制端 ◀── command { from: 对方, action: "queueState", payload: { queue, index } } ── 对方
```

- `queue` 用的是控制指令通道，`from` 就是应答要发回的收件人；被请求方漏了 `from` 的话，控制端永远收不到列表。
- `queueState.queue` 的结构与 `transfer.payload.queue` 相同（见第 9 节），**最多 200 首**：整条 payload 受 512 KB 上限约束，超了会被网关拒掉。
- `queueState` 只是一个数据应答，**不需要**再补报状态（它没改变任何播放状态）。

三个写操作，`index` 一律是**对方队列**的下标（从 0 开始），不是控制端自己的队列：

| action | payload | 语义 |
|---|---|---|
| `playAt` | `{ "index": 3 }` | 从第 4 首开始播（队列不变） |
| `remove` | `{ "index": 3 }` | 移除第 4 首；移的正好是当前这首时，对方接着播下一首 |
| `add` | `{ "track": { … } }` | 追加到队尾；对方已有同一 `key` 时会拒绝（由它自己提示） |

写完**重新要一次** `queue`：协议里没有「列表变了」这种增量事件，控制端手里那份只是某一刻的快照。

## 8. 接管播放的完整时序（重点）

这是整套协议里唯一有往返的地方，容易接错。

### 场景 A：把 A 的播放搬到 B

以 B 为控制端（界面上点「播到这台」，目标是自己）：

```
B ──POST command { deviceId: B, target: A, action: "release" }──▶ 网关
                                                                  │
                                        A ◀── command { from: "B", action: "release" }
                                        │
                                        A：暂停自己
                                        │
B ◀── command { from: "A", action: "transfer", payload: { queue, index, position } }
│
B：载入队列、从 position 继续播放
```

要点：**发起方只表达「我要接手」，队列由持有方回传。** 因为发起方本来就不掌握对方的队列。

### 场景 B：把 B 正在放的交由 A 播放

以 B 为控制端，目标是对端 A：

```
B：POST command { deviceId: B, target: A, action: "transfer",
                  payload: { queue: <B 自己的队列>, index, position } }
B：暂停自己（本地操作，不经网关）

A ◀── command { from: "B", action: "transfer", … }
A：载入队列、从 position 继续播放
```

**`transfer` 是单程的**（谁发起谁提供队列），**`release` 是一个往返**（发起方只表达意图）。

### 常见接错

| 现象 | 原因 |
|---|---|
| 点「播到这台」后，对端停了但本机不响 | 对端收到 `release` 后没有用 `command.from` 当收件人回传 `transfer` |
| 对端不回传 | 发 `release` 时漏填了 `deviceId`（发起方自己），导致 `from` 是空串 |
| 接过来能出歌但进度从头开始 | `transfer` 的 `position` 没带，或没在载入队列后 seek |
| 接过来播不了 | `queue` 里的曲目缺 `sources`，接收方拿不到 `platform` + `id` 去解析流 |

## 9. 播放队列的数据结构

`payload.queue` 的元素是各客户端共用的曲目结构（定义见 `web/src/api/types.ts`）：

```ts
{
  key: string,               // 曲目唯一键（如 "netease:186016"），去重与定位都用它
  title: string,
  artists: [{ name: string, id?: string, platform?: 'netease' | 'qq' }],
  album: { name: string, cover?: string, id?: string, platform?: 'netease' | 'qq' },
  durationMs: number,
  sources: [{ platform: 'netease' | 'qq', id: string, mid?: string, numericId?: string }],
  vip?: boolean
}
```

对接时的关键点：

- **`sources` 必须带上**。接收方要靠 `platform` + `id` 调 `/api/play/resolve` 换播放地址，缺了就播不出来。
- `artists[].id` / `album.id` 是**可选**的：缺了只是不能点进歌手/专辑详情页，不影响播放。
- 其它平台若已有自己的曲目模型，需要一层映射：至少保留 `key` / `title` / `artists[].name` / `album.name` / `album.cover` / `durationMs` / `sources`。多余字段可以丢。

## 10. 错误码

| HTTP | code | 场景 | 客户端该怎么办 |
|---|---|---|---|
| 400 | `invalid_device_id` | `deviceId` 为空或超过 64 字符 | 修 bug，别重试 |
| 400 | `too_many_devices` | 单账号同时在线超过 20 台 | 提示用户，或先断开其它设备 |
| 400 | `unknown_action` | `action` 不在白名单 | 修 bug |
| 400 | `payload_too_large` | payload 超过 512 KB | 限制队列长度（建议 ≤ 200 首） |
| 401 | `unauthorized` | 未登录 / 会话过期 | 跳登录；**SSE 收到 401 后不要重连** |
| 404 | `device_offline` | 目标设备不在线 | 刷新设备列表，提示"该设备已离线" |

注意 SSE 的失败不走 JSON：连接被拒时只会看到 HTTP 状态码，然后连接关闭。

## 11. 限制与边界

- **单账号最多 20 台设备**同时在线（再多会 `400 too_many_devices`）。
- **状态不落库**：网关重启后列表清空，各设备重连并重新上报即恢复。重启期间查询不到任何设备。
- **全量广播**：任何变化都推整份列表。设备数少时开销可忽略，但客户端要能接受重复内容。
- **心跳 25 秒**，服务端不做客户端侧超时清理，以 socket 断开为准。
- **注意单位**：`position` 与 `duration` 是**秒**，而 `track.durationMs` 是**毫秒**。两者不同源是刻意的（进度要参与秒级运算），照传即可，别再换算一次。

## 12. 各平台接入要点

### Android（Kotlin + Media3）

- **SSE**：用 `okhttp-sse` 的 `EventSource`，或手写流式读取。注意给这个 OkHttpClient 配上比普通请求更长的读超时。
- **指令处理要落在 Service 侧**：播放器活在 `MusicPlaybackService`（Media3 `MediaSessionService`）里，界面只是个遥控器。若把指令处理写在 ViewModel 里，用户退到后台就无法被其它设备操控了。
- **状态上报**从 `Player.Listener` 取：`onIsPlayingChanged`、`onMediaItemTransition`、`onPlaybackStateChanged` 时立即上报。**不要**加周期性上报 —— 进度由控制端推算。注意 Media3 不会为 seek 单独回调，所以要在包装 `Player.seekTo()` 的地方主动补报一次，或按 6.5 做偏差检测。
- **模式与播放列表的遥控**（7.6）已经接上：`ConnectSync` 在状态里上报 `playMode`（来自 `PlaybackCenter.playMode`），处理 `mode` / `playAt` / `remove` / `add` / `queue` / `queueState`；`queue` 的应答把本机队列映射成 `TrackSummary`，最多 200 首。`DeviceControlSheet` 里是四段式模式选择 + 可展开的播放列表。
- 连接的生命周期建议挂在 Application 级（收到登录态变化时启停），不要挂在 Activity。

### Windows

- 任意 HTTP 客户端都能接 SSE；确保连接在整个进程存活期内保持，并实现退避重连。
- 若接了系统媒体控制（媒体键、SMTC），远程指令应与本地媒体键走**同一个**播放器操作入口。

### 通用建议

- 执行完远程指令**立即补报状态**。
- 客户端本地操作与远程指令**共用同一套播放器方法**。
- 设备名给个能认出来的默认值（`Windows · Chrome` 这种），并允许用户改。
